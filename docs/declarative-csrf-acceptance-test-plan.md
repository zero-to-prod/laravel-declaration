# Declarative CSRF — Acceptance Test Plan (`csrf:`)

**Subject under test:** the manifest's `csrf:` key — **not yet implemented** (`[ ]` Missing in [declarative-framework-api-mapping.md](declarative-framework-api-mapping.md) Domain 2, proposed in [declarative-tier1-remaining.md](declarative-tier1-remaining.md) with native surface = URI exclusions). The declared surface, per the vendored docs, is the documented `Middleware::preventRequestForgery(except:, originOnly:, allowSameSite:)` configuration applied to `Illuminate\Foundation\Http\Middleware\PreventRequestForgery` — the middleware included in the default `web` middleware group ([middleware.md — Laravel's Default Middleware Groups](repos/laravel/docs/middleware.md#laravels-default-middleware-groups)). The proposed manifest shape mirrors the doc's calls one-to-one:

```yaml
csrf:
  except: ["stripe/*", "http://example.com/foo/bar", "http://example.com/foo/*"]
  originOnly: false
  allowSameSite: false
```

**Source documentation:** [docs/repos/laravel/docs/csrf.md](repos/laravel/docs/csrf.md) — the vendored Laravel docs are the **system of record** for every behavior below; supporting clauses are cited from [middleware.md](repos/laravel/docs/middleware.md), [routing.md](repos/laravel/docs/routing.md), [session.md](repos/laravel/docs/session.md), [helpers.md](repos/laravel/docs/helpers.md), [blade.md](repos/laravel/docs/blade.md), [errors.md](repos/laravel/docs/errors.md), and [http-tests.md](repos/laravel/docs/http-tests.md). This plan contains no behavior sourced from the framework code alone.

**Rule:** one **Given / When / Then** test per unique documented behavior. A test exists only where the vendored docs document the behavior; documented-but-non-declarable behavior is inventoried in §9. Tests are not implemented here.

**Harness prerequisite:** the CSRF middleware is *automatically disabled for all routes when running tests* ([csrf.md — NOTE](repos/laravel/docs/csrf.md#csrf-excluding-uris), [http-tests.md — Making Requests](repos/laravel/docs/http-tests.md#making-requests), tested as AT-18). Every test in §2–§7 must therefore re-enable CSRF protection for its request before the **When** step, and simulate the browser-supplied `Sec-Fetch-Site` header explicitly where a test's **Given** names it.

## 2. Default protection & inspection scope ([csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests))

### AT-01 — a tokenless state-changing request is rejected with `419`

**Doc says:** "we need to inspect every incoming `POST`, `PUT`, `PATCH`, or `DELETE` request for a secret session value that the malicious application is unable to access." and "any HTML forms pointing to `POST`, `PUT`, `PATCH`, or `DELETE` routes that are defined in the `web` routes file should include a CSRF token field. Otherwise, the request will be rejected." The rejection status: "the `419` response typically associated with CSRF token mismatches" ([csrf.md — Origin Verification](repos/laravel/docs/csrf.md#origin-verification)); "419 HTTP responses generated by invalid CSRF tokens" ([errors.md](repos/laravel/docs/errors.md#ignoring-exceptions-by-type)).

- **Given** CSRF protection is enabled and four `web`-group routes accept `POST`, `PUT`, `PATCH`, and `DELETE` respectively.
- **When** each route is requested without any `_token` field and without a passing `Sec-Fetch-Site` origin check.
- **Then** every request is rejected with a `419` HTTP response — each state-changing method was inspected for the secret session value and none carried it.

Sources: [csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests); [csrf.md — Origin Verification](repos/laravel/docs/csrf.md#origin-verification); [routing.md — CSRF Protection](repos/laravel/docs/routing.md#csrf-protection); [errors.md — Ignoring Exceptions By Type](repos/laravel/docs/errors.md#ignoring-exceptions-by-type).

### AT-02 — a valid `_token` field passes token validation

**Doc says:** "you should include a hidden CSRF `_token` field in the form so that the CSRF protection middleware can validate the request" — `<input type="hidden" name="_token" value="{{ csrf_token() }}" />`.

- **Given** CSRF protection is enabled, a `POST`-accepting `web`-group route, and the hidden `_token` field carrying the value of the current session's token (`csrf_token()`).
- **When** the form is submitted with the `_token` field and without a passing `Sec-Fetch-Site` origin check.
- **Then** the request passes — token validation validated the request against the session's secret value.

Sources: [csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests); [routing.md — CSRF Protection](repos/laravel/docs/routing.md#csrf-protection).

### AT-03 — a same-origin `Sec-Fetch-Site` request is allowed immediately, without token verification

**Doc says:** "First, the middleware checks the browser's `Sec-Fetch-Site` header. Modern browsers automatically set this header on every request, indicating whether it originated from the same origin, the same site, or a cross-site source. If the header indicates the request came from the same origin, the request is allowed immediately without any token verification."

- **Given** CSRF protection is enabled, a `POST`-accepting `web`-group route, and a request carrying the `Sec-Fetch-Site: same-origin` header.
- **When** the route is requested with no `_token` field and no `X-CSRF-TOKEN` header.
- **Then** the request is allowed immediately — the same-origin `Sec-Fetch-Site` check passed and no token verification ran at all.

Sources: [csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests).

### AT-04 — when `Sec-Fetch-Site` does not pass, the middleware falls back to token validation

**Doc says:** "If origin verification does not pass — for example, because the request comes from an older browser that doesn't send the `Sec-Fetch-Site` header or because the connection is not secure — the middleware falls back to traditional CSRF token validation."

- **Given** CSRF protection is enabled, a `POST`-accepting `web`-group route, and a request that does **not** send the `Sec-Fetch-Site` header (the doc's older-browser example) but does carry the valid current session token in its `_token` field.
- **When** the route is requested.
- **Then** the request passes — origin verification did not pass, so the middleware fell back to traditional CSRF token validation, which the valid token satisfied.

Sources: [csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests).

### AT-05 — safe methods are not inspected for a CSRF token

**Doc says:** "we need to inspect every incoming `POST`, `PUT`, `PATCH`, or `DELETE` request for a secret session value" — the inspection scope is enumerated as exactly those four methods.

- **Given** CSRF protection is enabled and a `GET` route in the `web` group.
- **When** the route is requested without any token and without a passing `Sec-Fetch-Site` origin check.
- **Then** the request succeeds — `GET` is outside the documented inspection scope, so no token verification applied.

Sources: [csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests) (the `An Explanation of the Vulnerability` clause).

## 3. Token & session ([csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests); [session.md](repos/laravel/docs/session.md); [helpers.md](repos/laravel/docs/helpers.md))

### AT-06 — `csrf_token()` retrieves the current session's token

**Doc says:** "Laravel automatically generates a CSRF "token" for each active [user session] managed by the application." and "The current session's CSRF token can be accessed via the request's session or via the `csrf_token` helper function" — `$token = $request->session()->token();` / `$token = csrf_token();` ([helpers.md — `csrf_token()`](repos/laravel/docs/helpers.md#method-csrf-token): "The `csrf_token` function retrieves the value of the current CSRF token").

- **Given** an active session with CSRF protection enabled.
- **When** `csrf_token()` is called and `$request->session()->token()` is called.
- **Then** both return the same value — the automatically generated token for the active session.

Sources: [csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests); [helpers.md — `csrf_token()`](repos/laravel/docs/helpers.md#method-csrf-token).

### AT-07 — the token changes when the session is regenerated

**Doc says:** "Since this token is stored in the user's session and changes each time the session is regenerated, a malicious application is unable to access it." ([session.md — Regenerating The Session ID](repos/laravel/docs/session.md#regenerating-the-session-id): "you may use the `regenerate` method").

- **Given** an active session whose token was used in a submitted `_token` field.
- **When** the session is regenerated (`$request->session()->regenerate()`).
- **Then** a fresh token is issued — the pre-regeneration token no longer validates a state-changing request, while the post-regeneration token does.

Sources: [csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests); [session.md — Regenerating The Session ID](repos/laravel/docs/session.md#regenerating-the-session-id).

## 4. Origin verification configuration ([csrf.md — Origin Verification](repos/laravel/docs/csrf.md#origin-verification))

### AT-08 — `originOnly: true` disables the CSRF token fallback entirely

**Doc says:** "if you would like to rely solely on origin verification and disable the CSRF token fallback entirely, you may do so using the `preventRequestForgery` method" — `$middleware->preventRequestForgery(originOnly: true);`

- **Given** the declared `csrf:` surface sets origin-only mode and a `POST` route carrying a **valid** current session token.
- **When** the route is requested with a `Sec-Fetch-Site` header that does not pass origin verification.
- **Then** the request is rejected — origin verification alone governs access; the valid token did not rescue the failed origin check because the token fallback was disabled entirely.

Sources: [csrf.md — Origin Verification](repos/laravel/docs/csrf.md#origin-verification).

### AT-09 — origin-only mode returns `403` instead of `419` for failed origin verification

**Doc says:** "When using origin-only mode, requests that fail origin verification will receive a `403` HTTP response instead of the `419` response typically associated with CSRF token mismatches."

- **Given** the declared `csrf:` surface sets origin-only mode.
- **When** a state-changing request fails origin verification.
- **Then** the response status is `403` — not the `419` produced by token-mismatch failures in default mode (AT-01).

Sources: [csrf.md — Origin Verification](repos/laravel/docs/csrf.md#origin-verification); [errors.md — Ignoring Exceptions By Type](repos/laravel/docs/errors.md#ignoring-exceptions-by-type).

### AT-10 — without HTTPS, origin verification is unavailable and token validation applies

**Doc says:** "> [!WARNING] The `Sec-Fetch-Site` header is only sent by browsers over secure (HTTPS) connections. If your application is not served over HTTPS, origin verification will not be available and the middleware will fall back to CSRF token validation."

- **Given** the declared `csrf:` surface sets origin-only mode and the application is served over plain HTTP (the test harness's default `http://localhost`).
- **When** a state-changing request without a valid token is made.
- **Then** the middleware fell back to CSRF token validation — the request receives the token-mismatch `419` response, not origin-only's `403`, because origin verification was unavailable over the insecure connection.

Sources: [csrf.md — Origin Verification](repos/laravel/docs/csrf.md#origin-verification).

### AT-11 — `allowSameSite: true` accepts same-site (subdomain) requests in addition to same-origin

**Doc says:** "If your application needs to accept requests from subdomains (for example, `dashboard.example.com` accepting requests from `example.com`), you may allow same-site requests in addition to same-origin requests" — `$middleware->preventRequestForgery(allowSameSite: true);`

- **Given** the declared `csrf:` surface sets `allowSameSite` and a `POST` route on `dashboard.example.com`.
- **When** the route is requested without a token, with a `Sec-Fetch-Site` header indicating a same-site source (a request originating from `example.com`).
- **Then** the request is accepted without token verification — same-site passed origin verification in addition to same-origin, per the doc's subdomain scenario.

Sources: [csrf.md — Origin Verification](repos/laravel/docs/csrf.md#origin-verification).

## 5. Excluding URIs from CSRF protection ([csrf.md — Excluding URIs](repos/laravel/docs/csrf.md#csrf-excluding-uris))

> The doc's three example patterns are three distinct documented exclusion shapes: a path wildcard, an exact full URL, and a full-URL wildcard.

### AT-12 — `except: ['stripe/*']` excludes matching URIs from CSRF protection

**Doc says:** "Sometimes you may wish to exclude a set of URIs from CSRF protection. For example, if you are using Stripe to process payments and are utilizing their webhook system, you will need to exclude your Stripe webhook handler route from CSRF protection since Stripe will not know what CSRF token to send to your routes." — `$middleware->preventRequestForgery(except: ['stripe/*', ...]);`

- **Given** the declared `csrf:` surface excludes `stripe/*` and a `POST` route at `stripe/webhook`.
- **When** the route is requested without any token and without a passing `Sec-Fetch-Site` origin check.
- **Then** the request succeeds — the excluded URI was not subjected to CSRF protection (Stripe sent no token). A sibling non-excluded `POST` route still rejects tokenless requests with `419`, proving the exclusion is scoped to the declared pattern.

Sources: [csrf.md — Excluding URIs](repos/laravel/docs/csrf.md#csrf-excluding-uris).

### AT-13 — an exact full URL in `except` excludes that URL

**Doc says:** the `except` example includes the exact URL `'http://example.com/foo/bar'`.

- **Given** the declared `csrf:` surface excludes `http://example.com/foo/bar` and a `POST` route served at that exact URL.
- **When** the route is requested without any token.
- **Then** the request succeeds — the exact URL matched the declared exclusion.

Sources: [csrf.md — Excluding URIs](repos/laravel/docs/csrf.md#csrf-excluding-uris).

### AT-14 — a full-URL wildcard in `except` excludes everything under it

**Doc says:** the `except` example includes the wildcard URL `'http://example.com/foo/*'`.

- **Given** the declared `csrf:` surface excludes `http://example.com/foo/*` and `POST` routes at `http://example.com/foo/bar` and `http://example.com/foo/bar/baz`.
- **When** both routes are requested without any token.
- **Then** both requests succeed — the full-URL wildcard covered every URI under `/foo/`.

Sources: [csrf.md — Excluding URIs](repos/laravel/docs/csrf.md#csrf-excluding-uris).

## 6. Request headers & cookie ([csrf.md — X-CSRF-TOKEN](repos/laravel/docs/csrf.md#csrf-x-csrf-token); [csrf.md — X-XSRF-TOKEN](repos/laravel/docs/csrf.md#csrf-x-xsrf-token))

### AT-15 — the `X-CSRF-TOKEN` request header is checked in addition to the `_token` POST parameter

**Doc says:** "In addition to checking for the CSRF token as a POST parameter, the `PreventRequestForgery` middleware will also check for the `X-CSRF-TOKEN` request header."

- **Given** CSRF protection is enabled, a `POST` route, and a request whose `X-CSRF-TOKEN` header carries the current session token, with no `_token` field.
- **When** the route is requested without a passing `Sec-Fetch-Site` origin check.
- **Then** the request passes — the header satisfied token validation in place of the POST parameter.

Sources: [csrf.md — X-CSRF-TOKEN](repos/laravel/docs/csrf.md#csrf-x-csrf-token).

### AT-16 — an encrypted `XSRF-TOKEN` cookie is included with each response

**Doc says:** "Laravel stores the current CSRF token in an encrypted `XSRF-TOKEN` cookie that is included with each response generated by the framework."

- **Given** an active session with CSRF protection enabled.
- **When** any response is generated.
- **Then** the response includes an `XSRF-TOKEN` cookie whose value decrypts to the current session's CSRF token — and whose raw value is encrypted, not the plaintext token.

Sources: [csrf.md — X-XSRF-TOKEN](repos/laravel/docs/csrf.md#csrf-x-xsrf-token).

### AT-17 — the `X-XSRF-TOKEN` header built from the cookie value grants passage

**Doc says:** "You can use the cookie value to set the `X-XSRF-TOKEN` request header." ([sanctum.md — CSRF Protection](repos/laravel/docs/sanctum.md#csrf-protection): "This token should then be URL decoded and passed in an `X-XSRF-TOKEN` header on subsequent requests").

- **Given** the `XSRF-TOKEN` cookie from a prior response, a `POST` route, and no `_token` field.
- **When** the route is requested with the `X-XSRF-TOKEN` header set to the URL-decoded cookie value and without a passing `Sec-Fetch-Site` origin check.
- **Then** the request passes — the cookie-derived header satisfied token validation.

Sources: [csrf.md — X-XSRF-TOKEN](repos/laravel/docs/csrf.md#csrf-x-xsrf-token); [sanctum.md — CSRF Protection](repos/laravel/docs/sanctum.md#csrf-protection).

## 8. Cross-referenced behavior ([blade.md](repos/laravel/docs/blade.md#csrf-field); [helpers.md](repos/laravel/docs/helpers.md#method-csrf-field); [errors.md](repos/laravel/docs/errors.md#ignoring-exceptions-by-type))

### AT-19 — the `@csrf` Blade directive generates the hidden `_token` input

**Doc says:** "Anytime you define an HTML form in your application, you should include a hidden CSRF token field in the form so that [the CSRF protection] middleware can validate the request. You may use the `@csrf` Blade directive to generate the token field" — `@csrf` is "Equivalent to..." `<input type="hidden" name="_token" value="{{ csrf_token() }}" />`.

- **Given** a Blade form containing the `@csrf` directive.
- **When** the form is rendered and submitted.
- **Then** the rendered form contains the hidden `name="_token"` input with the current session token as its value, and the submission passes CSRF validation.

Sources: [blade.md — CSRF Field](repos/laravel/docs/blade.md#csrf-field); [csrf.md — Preventing CSRF Requests](repos/laravel/docs/csrf.md#preventing-csrf-requests); [helpers.md — `csrf_field()`](repos/laravel/docs/helpers.md#method-csrf-field).

### AT-20 — `419` and `403` CSRF/origin failures are ignored by the internal error handler

**Doc says:** "Internally, Laravel already ignores some types of errors for you, such as exceptions resulting from 404 HTTP errors, 403 HTTP responses generated by origin mismatches, or 419 HTTP responses generated by invalid CSRF tokens."

- **Given** an application with exception reporting observable (log/report spy) and CSRF protection enabled.
- **When** a tokenless `POST` produces a `419` (and, in origin-only mode, a failed-origin request produces a `403`).
- **Then** no CSRF/origin-mismatch exception reaches the application's exception reporting — the framework ignores these internally (unless `stopIgnoring` is used, which is outside the `csrf:` surface).

Sources: [errors.md — Ignoring Exceptions By Type](repos/laravel/docs/errors.md#ignoring-exceptions-by-type); [csrf.md — Origin Verification](repos/laravel/docs/csrf.md#origin-verification). *(Errors-domain behavior; included because it documents the observable consequence of CSRF failures.)*
